# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ai-companion_0.13.0/` (nested folder of the same name) is a Factorio 2.x mod written in Lua. It spawns controllable "companion" characters and exposes ~51 RCON commands so an external AI/orchestrator (e.g. via a companion MCP server) can command them — move, mine, craft, build, fight, chat.

All real development happens in `ai-companion_0.13.0/`. (An earlier `bun init`-generated TypeScript stub used to sit at the repo root; it had no real logic and was removed.)

## Commands

There is no build/lint/test suite. This is a Factorio mod — "running" it means loading it in Factorio.

- **Install/deploy the mod** (copy into Factorio's mods folder):
  - Windows: `xcopy /E /I factorio-mod "%APPDATA%\Factorio\mods\ai-companion"`
  - Linux: `cp -r factorio-mod ~/.factorio/mods/ai-companion`
  - Mac: `cp -r factorio-mod ~/Library/Application\ Support/factorio/mods/ai-companion`
  - (Since this working copy already lives under `%APPDATA%\Factorio\mods\...`, in practice edits here take effect directly — just enable the mod and restart/reload in Factorio.)
- **Test changes**: launch Factorio with the mod enabled and RCON reachable (see below) and drive it through the `/fac` chat command or RCON commands.
- **Command reference**: run `commands_reference.bat` (Windows) to print the full syntax of every `/fac_*` RCON command, generated by hand from `control.lua` and `commands/*.lua`. Keep it in sync when adding/changing commands.
- **Syntax-check Lua**: no linter is configured; rely on Factorio's own log output (`factorio-current.log`) when the mod fails to load, since errors surface there rather than in a build step.

## RCON connection requirements

The mod's console commands (`fac_*`) are only reachable from outside the game over RCON, so an orchestrator/agent needs a live RCON connection to do anything beyond reading code.

- **Factorio must be running as a server with RCON enabled** — RCON is a Factorio launch-time flag, not something this mod configures itself (nothing in this repo sets the port/password). Typically started with `--start-server <save>` plus `--rcon-port <port> --rcon-password <password>` (or the equivalent server-settings.json fields).
- **The mod's own README states port `25575`, password `factorio`** (`ai-companion_0.13.0/README.md`, corrected 2026-08-09 from a stale `27000` after verifying against the live process) — still just documentation, not a guarantee for every environment.
- **Verified actual port on this machine's running server: `25575`** (confirmed 2026-08-09 via `Get-NetTCPConnection -State Listen -OwningProcess <factorio pid>`, which showed `127.0.0.1:25575`, plus a successful `Test-NetConnection` against it). The password isn't independently verifiable from outside the process; go with what's already allowlisted/working in `.claude/settings.local.json` and the `factomcp` tool config.
- This port is set at server launch time (`--rcon-port`/server-settings), so it can change if the server is restarted with different flags — re-verify rather than trusting this note if RCON connections start failing.
- **Useful verification steps** (Windows, matching what's already allowlisted in `.claude/settings.local.json`):
  - Confirm the server process is up and get its PID: `Get-Process factorio -ErrorAction SilentlyContinue | Select-Object Id,ProcessName,StartTime`
  - Find the actual listening RCON port for that PID: `Get-NetTCPConnection -State Listen -OwningProcess <pid> | Select-Object LocalPort`
  - Confirm the port is accepting connections: `Test-NetConnection -ComputerName 127.0.0.1 -Port <port> | Select-Object TcpTestSucceeded`
- **In this environment, prefer the `factomcp` MCP tools** (`mcp__factomcp__*`, e.g. `run_lua`, `scan_area`, `walk_to`, `mine_resource`) over hand-rolling raw RCON calls — they're already wired to the running server and are what's allowlisted for use here.
- A `[AI Companion] v<version> ready` chat message on world load (from `control.lua`'s `on_init`) confirms the mod itself loaded; it does not confirm RCON is reachable — those are independent failure points.

## Architecture

### Storage model
All mutable mod state lives in Factorio's `storage` table (persisted across saves), initialized in `control.lua`'s `init_storage()`:
- `storage.companions[id]` — `{entity, color, label, name?}` for each spawned companion
- `storage.companion_messages` — chat message queue (player → AI, AI → companion), trimmed by `cleanup_messages()` on a timer
- `storage.walking_queues[id]` — pathing/follow state processed every 5 ticks in `control.lua`
- `storage.harvest_queues` / `storage.craft_queues` / `storage.build_queues` / `storage.combat_queues` — tick-based action queues owned by `commands/queues.lua`
- `storage.companion_markers[id]` — map chart tags kept in sync with companion position
- `storage.context_clear_requests` / `storage.errors` — bookkeeping for the orchestrator side
- `storage.goals[id]` — persistent goal/task ledger owned by `commands/goals.lua` (see below)

### Two command surfaces, same underlying logic
1. **`commands.add_command("fac_*", ...)`** — RCON/console commands, one file per domain under `commands/` (`action`, `building`, `chat`, `companion`, `context`, `goal`, `item`, `move`, `research`, `resource`, `world`, `combat`, `help`), each `require`d from `control.lua`. This is the primary interface an external orchestrator drives via RCON (see `commands_reference.bat` for the full list).
2. **`remote.add_interface("ai_companion_bridge", {...})`** in `control.lua` — a Lua-callable bridge exposing the same capabilities as plain functions, for callers that can't reach console commands via RCON (`remote.call`).

Both surfaces are thin wrappers around shared logic in `commands/init.lua` (utilities: companion lookup, colors, direction math, JSON responses) and `commands/queues.lua` (the tick-based action state machines). When adding a new capability, put the actual behavior in `queues.lua`/`init.lua` and expose it from both the relevant `commands/*.lua` file and the bridge if orchestrators need non-RCON access.

### Instant vs. tick-based ("realistic") actions
Most domains offer two flavors of the same action:
- **Instant**: e.g. `fac_item_craft`, `fac_building_place` — resolves immediately, teleport-like.
- **Tick-based** (`*_start` / `*_status` / `*_stop`): e.g. `fac_item_craft_start`, `fac_resource_mine_start`, `fac_building_place_start`, `fac_action_attack_start` — enqueues into one of the `storage.*_queues` tables and progresses over real ticks via `queues.tick_harvest_queues()`, `tick_craft_queues()`, `tick_build_queues()`, `tick_combat_queues()`, all driven from the `script.on_nth_tick(5, ...)` handler in `control.lua`. Mining specifically is "hybrid": it lets Factorio's native `mining_state` do the work rather than reimplementing mining itself, and tracks yield by recomputing the inventory delta against the snapshot taken at `start_harvest` on every tick (see `queues.lua`'s harvest section) — advancing to the next resource entity is driven by that entity's `valid` flag, not by `mining_state` toggling false, since `mining_state` can stay `true` indefinitely on a single tile richer than the target count (this was a real bug: the original version only recounted on that toggle, so the harvested counter silently never advanced on rich ore patches even though ore kept accumulating).

Follow ("`move_follow`") and general walking use a separate `storage.walking_queues` loop in `control.lua` (not in `queues.lua`), including stuck-detection/sidestep logic to get companions unstuck from terrain.

### Response format
RCON command handlers respond via `u.json_response(data)` (success) or `u.error_response(msg, ctx)` (failure, also logged to `storage.errors`), both JSON-serialized through `rcon.print`. Handlers are wrapped in `u.safe_command(fn)` (pcall) so a Lua error becomes a JSON error response instead of crashing the mod. Keep this pattern for any new command.

### Companion identification
Companions are referenced by numeric id or by name via `u.find_companion(identifier)` (checks numeric id first, then case-insensitive name match) throughout both the command layer and the bridge — reuse it rather than indexing `storage.companions` directly.

### Goal/task tracking
`commands/goals.lua` (logic, mirrors `queues.lua`'s style) plus `commands/goal.lua` (`fac_goal_*` RCON commands) implement a persistent ledger of goals in `storage.goals`, since nothing else in the mod keeps history — the action queues are ephemeral and vanish on completion. A goal is `{id, companion_id, description, status, watch_type, note, created_tick, updated_tick}` with `status` one of `pending`/`in_progress`/`done`/`failed`. `companion_id` is optional — omit it (bridge: leave `id` nil/empty; console: pass `-`) for a shared goal not tied to any one companion, e.g. a strategic milestone spanning multiple companions or the player's own objective. A `watch_type` requires a real `companion_id`, since auto-resolution watches that companion's action queues. Two ways to resolve a goal:
- **Auto**: pass `watch_type` (`"harvest"`/`"craft"`/`"build"`) to `goals.create()` — `queues.lua` calls `goals.resolve_watch(cid, watch_type, success, note)` at each point a matching queue finishes (target reached, ran out of resources, placement failed, etc.), which flips any `in_progress` goal for that companion/type to `done` or `failed`.
- **Manual**: goals without a `watch_type` (or for actions outside the queue system, like walking somewhere) stay `pending`/`in_progress` until something calls `goals.update(goal_id, status, note)` — in practice, the orchestrator driving the mod.

### A note on RCON access patterns
Registered console commands (`commands.add_command("fac_*", ...)`) are only invocable by something that can send a raw console/chat command line — typing in-game, or an RCON client sending literal text. An agent whose only tool runs arbitrary Lua over RCON (Factorio's `/sc`/`/c`-style execution) **cannot** reach `fac_*` commands that way, and that same execution context has its **own separate `storage`**, distinct from this mod's `storage` — direct `storage.companions[...]` access or `require(...)` from that context will fail. The one thing that *does* work from arbitrary Lua is `remote.call("ai_companion_bridge", "function_name", ...)`, since `remote.call` runs inside the mod's own environment. Practical upshot: when driving this mod from an LLM/agent tool that only exposes "run Lua via RCON," use the bridge functions, not the `fac_*` commands — and remember that editing `control.lua` has no live effect until the mod's script actually reloads (save reload or game restart), so a freshly-added bridge function will 404 (`No such function`) until then.
